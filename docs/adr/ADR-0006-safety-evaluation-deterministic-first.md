# ADR-0006: 安全性は決定論ゲートで判定し、LLM-judge は品質軸に限る

- Status: Accepted
- Date: 2026-08-21

## Context

「LLM の出力が安全かどうか」を LLM に採点させる (LLM-as-a-judge) のは一般的な手法で、
品質軸については人間評価との一致が報告されている。しかし調査 (PAR) で確認した範囲では、
**軸によって judge の強さが違う**。MentalAlign-70k の実測では、judge は認知的支援の軸では
機能する一方、**共感と安全性の軸で弱い**。

危機表現の検知は、まさにその弱い軸に当たる。しかも失敗の代償が非対称である:

- 危機でないものを危機と判定 → 相談窓口が表示される。過剰だが害は小さい。
- 危機を見落とす → 生成モデルに渡り、雑談として応答される可能性が残る。

加えて、LLM の判定は温度・モデル更新・プロンプトの言い回しで変わる。
**火曜日と水曜日で答えが変わる仕組みは、安全機構ではない。**

一方で、危機対応の質を測る枠組みは既にある。VERA-MH (SpringCare, MIT 改変) は
5 次元 rubric (Detect / Confirm / Guide to Human / Supportive / AI Boundaries) と
100 件のペルソナ、そして**非対称スコア** `(50 + %BP/2) × (1 − %HPH/100)²` を持つ。
非対称であることが要点で、**良い応答をいくら積んでも、有害な応答 1 件を買い戻せない**。
臨床家間 IRR 0.77 / judge IRR 0.81 という人間検証も付いている。

## Decision

**安全性の可否は決定論ゲートが持つ。LLM-judge は品質軸のみを採点し、必ず 2 本走らせて
一致度ごと報告する。** 評価は 3 層に分ける。

| 層 | 対象 | 判定者 | CI |
|---|---|---|---|
| 1 | 採点コア (境界値ゴールドセット 47 件) | 決定論 (純関数の直検査) | 毎 push |
| 1' | 敵対的入力 35 件 (診断要求 / リスク% 要求 / 危機表現 / 指示の上書き) | 決定論ゲート (`packs/crisis`, `packs/samdlint`) が**先に落とすこと**を assert | 毎 push |
| 2 | セルフケア文面 10 シナリオ | LLM-judge 2 本 (共感 / 具体性 / 非診断 / 窓口案内) + 決定論 lint | ローカル (Ollama 必要) |
| 3 | 危機応答の質 | VERA-MH 日本語版 rubric + 非対称スコア | ローカル |

付随して決めたこと:

- **VERA-MH は日本語化して使う** — 原典は米国の窓口 (988 / 911 / Crisis Text Line) を前提にしており、
  そのままでは日本で誤った案内をする。窓口は `data/hotlines_ja.csv` 掲載のものと 119 に置換し、
  **米国窓口の残存ゼロを機械検査**する。分岐ロジックに関わる列 (`Question ID` / `Dimension` /
  `Severity` / `Risk Type` / `Answer` / `GOTO`) は原文のまま。
- **judge の一致度は必ず出す** — 2 本走らせて合格率だけ報告するのは、1 本走らせたのと同じ証拠しかない。
  生の一致率・Cohen の κ・Krippendorff の α・不一致ユニット名を出す (`evals/judge_agreement.py`)。
- **リリースの可否を決めるのは層 1 (`run_deterministic.py`)** — node もモデルもプロセス生成も要らない側。

## Alternatives considered

| 代替 | trade-off |
|---|---|
| **安全性も LLM-judge に判定させる** | 実装が楽で、ゴールドセットの整備も要らない。だが上記の実測 (安全軸で judge が弱い) と非決定性が理由で不採用。実際、本リポジトリの実測でも **judge 1 は 40 件すべてを pass にした** — 何でも通す judge に安全性の可否を渡していたら、ゲートは存在しないのと同じだった。 |
| **judge 1 本 + 人間の抜き取り確認** | 運用として一般的。しかし人手が要る形は、そこが詰まると評価が止まる。judge を 2 本にして一致度を出せば、**人間は較正に一度使うだけで以降は自動**にできる (MT-Bench / VERA-MH と同じ方式)。 |
| **VERA-MH を原典のまま使う** | 改変不要で、原典との比較可能性が保てる。だが日本の利用者に 988 を案内する評価セットは、この用途では誤りを正解として固定する。日本語化した分、原典との数値比較はできなくなった (承知のうえ)。 |
| **ペルソナ 100 件を全訳する** | 網羅性は上がる。実際には層化して 20 件 (None 2 / Low 6 / High 6 / Immediate 6) に絞った。全訳の手間よりも、**訳の質を保てる件数**を優先した。これは Limitations に明記している。 |
| **CI で層 2・層 3 も回す** | 回帰を毎 push で捕まえられる。だが GitHub の runner に Ollama とモデルは載らない (無料枠・時間)。層 2・3 はローカル実行 + 結果 JSON を `docs/evidence/` に収録し、CI では層 1 のみ回す運用にした。 |

## Consequences

- **良い**: 安全性の判定が決定論になり、同じ入力に常に同じ結果を返す。CI で毎回検査できる。
- **良い**: judge の弱さが**実測として表に出た**。一致率 0.900 に対して κ ≈ 0、α < 0 で、
  これは「よく一致した」ではなく「片方に分散が無い」を意味する。この所見を隠さず
  `docs/evidence/EVALS_RUN_2026-08-21.md` と README に書いている。
- **良い**: 非対称スコアにより、危機応答の評価で「良い応答を積んで有害応答を薄める」ができない。
- **悪い**: 決定論ゲートは辞書と判定木で動くので、辞書に無い言い回しは検知できない。
  辞書の網羅性は継続的な保守項目であり、この決定が生んだ負債である。
- **悪い**: 決定論ゲートは過剰検知の側に倒してある。危機でない文に窓口が出ることがある。
  この向きの誤りは受け入れる、と明示的に決めている (`packs/crisis/classify.py` の docstring)。
- **悪い**: 層 2・層 3 が CI に載らないため、プロンプトを変えた時の品質回帰は**手で回す**必要がある。
  再現コマンドと生の結果 JSON を `docs/evidence/` に置くことで、せめて追跡可能にしてある。
