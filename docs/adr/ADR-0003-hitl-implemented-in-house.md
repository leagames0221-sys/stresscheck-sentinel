# ADR-0003: HITL は自作し、既存フレームワークの意味論を写像する

- Status: Accepted
- Date: 2026-08-21

## Context

ストレスチェック指針は、実施者 (医師等) に委ねてよい事務と、委ねてはいけない判断を分けている。
逐語では、AI に任せられるのは「調査票の回収、集計若しくは入力又は受検者との連絡調整等の実施の事務」、
任せられないのは「面接指導を受ける必要があるか否かを確認しなければならない」の側である。

つまり本ツールに必要なのは、飾りのレビュー画面ではなく、
**人間の決定が入るまで下流に何も流れない状態機械**である。

この形は既に一般解がある。調査 (PAR) で読んだ範囲では:

- **LangGraph の `interrupt()`** — 中断を例外として投げ、再開時は保存済みの値を返す。
  interrupt の id は「グラフ上の位置から決まる決定論的ハッシュ」で、同じ位置の中断は同じ id になる。
  再開時にノードの**先頭から再実行される**ため、副作用は interrupt より後か冪等でなければならない。
- **LangChain v1 の Human-in-the-loop middleware** — 決定型が
  `approve` / `edit` / `reject` / `respond` の 4 つ。`respond` はモデル出力を採らず人間の応答を返す経路。
  さらに **decisions を空にしたまま起動すると `ValueError`** で落ちる (ゲートを設定し忘れたまま
  「有効なつもり」で動く事故を、起動時に潰している)。

依存として入れると `langgraph` + `langgraph-checkpoint-sqlite` で推移的依存が 6 個。
数としては健全だが、ADR-0002 の「ランタイム依存ゼロ」を破る。

## Decision

**HITL は `src/sentinel/core/hitl.py` に自作し、上記の意味論を写像する。langgraph は採用しない。**

写像した内容と、写像元:

| 借りた設計判断 | 本実装 |
|---|---|
| 中断 id は位置から決まる決定論的ハッシュ (LangGraph) | `id = sha256(f"{token}:{stage}")[:16]`。同じ受検・同じ段階なら常に同じ id = 二重登録が起きない |
| 再開は保存値を返す / 再実行に耐える (LangGraph) | 状態は SQLite に永続化。`PENDING` 以外への `resume` は `StateError`。副作用 (通知の組み立て) は `SIGNED` 遷移後にのみ発生 |
| 決定型は 4 つ (LangChain v1) | `approve` / `edit` / `reject` / `respond`。`respond` は AI 出力を捨てて実施者の所見をそのまま採用する経路 |
| 空設定は起動時に落とす (LangChain v1) | ゲート設定が空なら `GateChain.__init__` が `GateSetupError` (= `ValueError` 系) を送出。禁止語辞書 0 件・危機タクソノミ 0 件でも同じ |

さらにこのツール固有の要求として、人間による上書き (`edit` / `reject` / `respond`) を全件記録し、
**オーバーライド率**を KPI として出す (`sentinel kpi`)。監視すべきは「人間がレビュー画面を通した回数」
ではなく「人間が AI の出力を採らなかった割合」である。

## Alternatives considered

| 代替 | trade-off |
|---|---|
| **langgraph を依存に入れる** | 実装量は減り、checkpoint も既製品で済む。代償は (1) ADR-0002 の依存ゼロを破ること、(2) このツールで必要なのは 1 段の中断であって、グラフ実行基盤の 95% は使わないこと。加えて、**フレームワークを理解していることの証明としては、写像して ADR に出典を書く方が強い** (import した事実は理解を示さない)。 |
| **prebuilt の `HumanInterrupt` を写す** | 一段楽になる。ただし調査時点で **deprecated**。写す対象として不適切。 |
| **決定型を `approve` / `reject` の 2 つにする** | 単純。しかし実施者が現実にやるのは「文面を直して出す」(`edit`) と「AI の文章は使わず自分の所見を書く」(`respond`) であり、この 2 つを潰すと、実施者は画面の外 (メール等) で仕事をすることになる。**記録に残らない経路を作るのが最悪**なので、4 つを維持した。 |
| **レビュー UI は作るが、ゲートはアプリ側の if で済ませる** | 早い。ただし「署名が無いのに下流へ流れた」を防ぐ根拠が、呼び出し側の書き忘れに依存する。ゲートを `GateChain` として独立させ、`release` 経路が必ず通るようにした。 |

## Consequences

- **良い**: 依存ゼロを維持したまま、フレームワークの設計判断 (id の決定論性・空設定で落とす・4 決定型)
  を実際に使えている。それぞれが単体テストで検証されている。
- **良い**: 再開時の二重実行が構造的に起きない (`PENDING` 以外は `StateError`)。
  再実行に耐える設計は、写像元が「ノード先頭から再実行される」という制約を持っていたから来た。
- **悪い**: LangGraph の他の機能 (分岐・並列・時間旅行) は当然無い。必要になったら
  自作を捨てて依存を入れる判断をやり直すことになる。その時はこの ADR を Superseded にする。
- **悪い**: 「写像した」と言えるのは意味論までで、langgraph の実装細部と挙動が完全一致する保証はない。
  一致を主張していない。主張しているのは、本実装がこのツールの要件を満たすこと。
